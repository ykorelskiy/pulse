# ТЗ: Озвученные ролики (Reels/Shorts/TikTok) — следующий этап после стабильной работы статики

Статус: **не MVP, отдельная фаза после того, как основной конвейер (картинка → Telegram → сайт → VK/Instagram) стабильно работает**. Модуль ощутимо сложнее предыдущих — впервые появляется синхронизация текста, звука и движения по кадру, а не просто вызов API и публикация готового файла.

---

## 1. Идея в двух словах

Кроме статичной картинки-плаката — короткий вертикальный ролик (9:16), где дикторский голос бодро проговаривает новости дня («Сегодня, 8 августа 2026 года — в Сибири нашли золото...»), а камера в это время панорамирует/наезжает на соответствующий фрагмент уже готовой картинки. Публикуется в Instagram Reels, YouTube Shorts, TikTok — один и тот же файл, формат у площадок совместимый.

Статичная картинка при этом продолжает публиковаться как раньше и остаётся с подписью, где перечислены источники — то, что можно спокойно прочитать и проверить. Ролик — эмоциональный вход, картинка — для тех, кто хочет разобраться подробнее.

---

## 2. Ключевая техническая развилка: откуда брать координаты для наездов камеры

Это самое узкое место всего модуля.

**Ненадёжный вариант — определять зоны постфактум по смыслу**, отправив готовую картинку в мультимодальную модель с вопросом «где на изображении сцена про золото, где про контейнеровоз». Проблема: это семантическая задача («что здесь изображено») без чётких границ, ошибки почти гарантированы на плотной композиции с мелкими деталями.

**Рекомендуемый вариант — нумерация через image-edit одного и того же файла.**

1. Финальная картинка генерируется как обычно (Модуль Г, без изменений) — она же уходит в публикацию, без цифр.
2. Сразу после этого — **не новая генерация, а вызов API в режиме редактирования именно этого файла** (image-edit, доступно и у gpt-image-1, и у Gemini/Nano Banana): модели даётся задача добавить поверх уже готовой картинки маленькие пронумерованные кружки-метки на сценах, соответствующих новостям 1–5 по порядку из брифа.
3. Важно, что это **редактирование того же изображения, а не независимая повторная генерация** — композиция гарантированно совпадает с опубликованной версией, отличаются только добавленные метки. Если делать это второй самостоятельной генерацией с нуля, большинство image-API не гарантируют идентичную композицию между двумя вызовами даже с одинаковым промптом — тогда цифры будут указывать не туда, куда нужно.
4. На пронумерованной версии ищем расположение цифр — это уже не смысловое распознавание, а поиск явных числовых меток: надёжная, решённая задача что для OCR, что для мультимодальной модели с вопросом «в каких координатах находится метка с цифрой N».
5. Найденные координаты переносятся на чистую (опубликованную) версию как есть — система координат общая, потому что это буквально один и тот же файл до/после редактирования.

Этот подход не ограничивает творческую свободу генерации (в отличие от идеи с жёсткой сеткой квадрантов) — модель складывает композицию естественно, а зоны определяются уже по готовому результату, но надёжно, а не на глаз.

Пронумерованная версия используется только внутри пайплайна для определения координат — публиковать её не нужно, чтобы не портить «шараду» для тех, кто разгадывает картинку в обсуждениях (Модуль Ж).

## 3. Пайплайн (по шагам)

### Шаг 1 — Определение зон: нумерованная версия через image-edit
После того как Модуль Г сгенерировал финальную картинку (без изменений в самом Модуле Г), выполняется дополнительный вызов image-edit API на этом же файле — модель добавляет пронумерованные метки на сценах, соответствующих новостям 1–5 из брифа. Результат — карта зон:
```json
[
  { "news_item_id": "...", "label": 1, "bbox": [0, 0, 0.5, 0.33] },
  { "news_item_id": "...", "label": 2, "bbox": [0.25, 0.33, 0.75, 0.66] },
  ...
]
```
`bbox` — относительные координаты (0–1 от размеров картинки) вокруг найденной метки с запасом на саму сцену, не пиксельные значения, чтобы не зависеть от итогового разрешения. Пронумерованная версия используется только для этого шага и никуда не публикуется.

### Шаг 2 — Сценарий озвучки (LLM)
Отдельный вызов LLM: на входе — сегодняшний бриф (новости с `ru_headline`), на выходе — связный дикторский текст, разбитый на реплики по одной на новость, в бодром разговорном тоне, с естественными связками («а вот это уже интереснее», «и пока одни считают золото...»). Длина — с прицелом на 30-45 секунд итогового ролика (это ограничивает суммарное число слов, стоит явно указать в промпте целевой хронометраж).

Формат вывода:
```json
[
  { "news_item_id": "...", "text": "Сегодня, 8 августа, в Сибири нашли золото — да не абы где, а прямо..." },
  { "news_item_id": "...", "text": "Пока одни радуются находке, у берегов..." }
]
```

### Шаг 3 — Синтез речи (TTS)
Каждая реплика озвучивается отдельным вызовом TTS — так на выходе сразу известна длительность каждого сегмента (по длине аудиофайла), и не нужен отдельный шаг принудительного выравнивания текста под таймкоды.

- Для русской озвучки — сервис с качественными RU-голосами (Yandex SpeechKit или аналог с хорошим произношением на RU), а не англоязычные TTS с плохим акцентом на русском.
- Стоимость — по символам, при 1 ролике в день это копейки, но не ноль — заложить как отдельную статью расходов, отдельную от TTS-бесплатных частей конвейера.

### Шаг 4 — Сборка видео
- Инструмент: ffmpeg (zoompan-фильтр) или moviepy поверх него — оба бесплатны, работают локально/на сервере без внешнего API.
- Для каждого сегмента: длительность = длительность его аудиофайла (из шага 3); движение камеры = плавный наезд/панорама от общего плана к `bbox` этой зоны (классический Ken Burns эффект).
- Аудиодорожка — последовательная склейка сегментов из шага 3, один к одному с видеосегментами.
- **Вшитые субтитры обязательны, не опционально** — подавляющее большинство просмотров в Reels/Shorts/TikTok идёт без звука; без субтитров ролик для такой аудитории бесполезен независимо от качества озвучки.
- Фоновая музыка (тихим фоном) — только из каталога с расчищенными правами (royalty-free/лицензия для коммерческого использования), иначе площадки блокируют звук или ролик целиком по Content ID — на этом легко потерять уже готовый контент задним числом.

### Шаг 5 — Публикация
Тот же принцип единой точки одобрения (Модуль Д), что и у картинки — ролик тоже уходит админу на подтверждение перед публикацией, отдельным сообщением вместе со статичной картинкой.

| Площадка | Особенности публикации |
|---|---|
| Instagram Reels | Через тот же Instagram Graph API, что и обычный пост, но `media_type = REELS`, видео тоже должно быть доступно по публичному URL, не файлом напрямую |
| YouTube Shorts | YouTube Data API v3, метод `videos.insert`, нужна отдельная OAuth-авторизация канала (разово настраивается) |
| TikTok | TikTok Content Posting API — процесс одобрения приложения у TikTok обычно дольше и придирчивее, чем у Meta/Google; на старте этой фазы разумно публиковать в TikTok вручную (просто скачивая готовый файл), пока не пройдено одобрение, а не блокировать весь модуль ожиданием TikTok |

## 4. Модель данных

```sql
create table issue_video_segments (
  id uuid primary key default gen_random_uuid(),
  issue_id uuid references issues(id),
  news_item_id uuid references news_items(id),
  order_index int,
  script_text text,
  audio_url text,
  duration_seconds numeric,
  bbox jsonb          -- [x0, y0, x1, y1] относительные координаты зоны наезда
);

create table issue_videos (
  id uuid primary key default gen_random_uuid(),
  issue_id uuid references issues(id),
  video_url text,
  status text default 'draft',  -- draft | approved | published
  created_at timestamptz default now()
);
```

## 5. Про статичную картинку с источниками (уже частично решено, уточнение)

- Полноценные кликабельные ссылки в подписи работают в Telegram и на сайте — там ничего менять не нужно.
- В Instagram обычные посты и Reels не поддерживают кликабельные ссылки в подписи — поэтому единственный практичный вариант: подпись содержит текстом список источников (не гиперссылки) + «ссылка в шапке профиля» ведёт на архивную страницу сайта, где всегда актуальный сегодняшний выпуск со всеми настоящими ссылками. Это уже согласуется с тем, что сайт (фаза 2 основного плана) и так задуман как архив с историей выпусков.

## 6. Рекомендация по порядку реализации внутри этой фазы

1. Шаг 1 (нумерация через image-edit) и Шаг 2 (сценарий) — можно и нужно тестировать вручную, без кода: прогнать пару готовых картинок через image-edit с запросом на нумерацию, глазами оценить, насколько точно модель ставит метки именно на нужные сцены, и отдельно — насколько связно получается озвучка. Это дешёвая проверка гипотезы до того, как писать сборку видео.
2. Только после того как нумерация выглядит достаточно точной на нескольких ручных прогонах — переходить к Шагам 3-4 (TTS + ffmpeg-сборка).
3. Публикацию (Шаг 5) добавлять последней и по одной площадке за раз — начать с Instagram Reels (раз он уже частично настроен по прошлому ТЗ), потом YouTube, TikTok — по готовности апрува или вручную.
