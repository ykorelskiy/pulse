# Проект: «Пульс дня» — ежедневный генеративный дайджест-плакат

## Варианты названия

- **Пульс.Арт** / **PulseArt** — коротко, отражает суть (пульс дня → картинка)
- **Мифдня** / **MythOfTheDay** — отсылка к твоей любимой стилистике «мифотворчества дня»
- **Зеркало дня** — по мотивам твоей же формулировки идеи
- **Днюха** — панковское, легко запоминается, годится для RU-аудитории
- **Пикча дня / PicOfTheDay.bot** — максимально прямолинейно и понятно с первого взгляда

Дальше в документе использую рабочее имя **Pulse** — легко заменить в коде одной константой.

---

## 1. Суть продукта

Ежедневно (в 18:00) автоматически генерируется одна насыщенная иллюстрация-плакат в стиле «плотный коллаж с пасхалками», отражающая:
- ключевые новости дня (через призму сатиры/аллегории, не буквально);
- ключевые слова, присланные пользователями в Telegram-боте;
- сквозных персонажей/мемы канала (маскот, повторяющиеся шутки — это то, что превращает разовый контент в узнаваемую вселенную, как у тебя робот Claude — сквозной герой).

Публикуется в Telegram-канал + сохраняется в архив на сайте. Вторая фаза — «прогноз на завтра» и сравнение прогноз/факт.

## 2. Архитектура (высокоуровнево)

```
[RSS/новости] ──┐
                 ├──> [Агрегатор контекста] ──> [Промпт-инженер (LLM)] ──> [Image API] ──> [Публикатор] ──> Telegram-канал
[Telegram-бот] ──┘                                                                                  │
      │                                                                                              ▼
      └──> [БД: слова, лайки, юзеры]                                                          [Архив/сайт]
```

**Компоненты:**

| Компонент | Роль | Технология |
|---|---|---|
| Telegram-бот | Сбор слов от пользователей | aiogram (Python) или node-telegram-bot-api |
| БД | Хранение слов, новостей, истории картинок | Supabase (Postgres), free tier |
| Агрегатор новостей | Сбор новостного фона дня | Python + feedparser (RSS) |
| Промпт-инженер | LLM превращает сырые данные в детальный промпт под стиль | Claude API / GPT API |
| Image API (слой абстракции) | Генерация самой картинки | gpt-image-1 (OpenAI) как основной; Gemini 2.5 Flash Image («Nano Banana») как альтернатива — сделать переключаемым, т.к. неясно, какой лучше держит стиль на регулярной основе |
| Оркестрация | Расписание запусков | GitHub Actions cron (бесплатно) |
| Публикатор | Постинг в канал + сохранение в архив | Telegram Bot API |
| Сайт (фаза 2) | Архив, календарь, топ-слова | Next.js на Vercel |

### Структура Telegram-сущностей

Три разные сущности с разными ролями — это разводит потоки данных и снимает вопрос авторизации:

1. **Канал** (публичный, read-only для всех) — сюда уходят только готовые, утверждённые тобой картинки. Никаких постов от пользователей. Подписаться может кто угодно.
2. **Discussion-группа**, привязанная к каналу (стандартная Telegram-функция «обсуждения») — здесь живут комментарии-разгадки (Модуль Ж). Комментировать может любой, у кого есть Telegram-аккаунт — сам факт наличия аккаунта уже и есть авторизация, отдельного логина не нужно. `user_id` из Telegram — это и есть идентификатор пользователя в таблице `guesses`.
3. **Бот сбора слов** (личка с ботом, отдельный от канала) — сюда пользователь один раз жмёт `/start` (это и есть регистрация — `user_id` сохраняется в БД), и дальше может присылать одну фразу дня раз в 24 часа. Лимит считается по `user_id` + `created_at` в таблице `words` (запрет, если уже есть запись за последние 24 часа).

Итог: канал и группа — публичная витрина и общение, бот — приватный канал ввода данных с естественной защитой от спама через `/start`-регистрацию.

## 3. Слой контентной стратегии («на грани фола», но без пробива стены модерации)

Это отдельный логический модуль, и его стоит вынести в промпт-инженере как самостоятельный этап — «редакционная политика».

**Принцип:** сатира через аллегорию и символы, а не через прямые фотореалистичные лица политиков.

Практическая причина: image-API технически блокируют реалистичные изображения узнаваемых живых политиков — это не обходится промптом, значит систему нужно проектировать вокруг этого ограничения, а не против него.

Рабочие приёмы для «остроты» без блокировки:
- **Символ вместо лица** — страна/институт/событие через узнаваемый визуальный код (герб, цвет, характерное здание, животное-символ, повторяющийся предмет), а не через портрет конкретного человека.
- **Абсурдистское преувеличение события**, а не персоны — высмеивается ситуация, а не физиономия.
- **Сквозные вымышленные персонажи-комментаторы** (как демон-«специалист по проблемам» на твоей картинке) — они дают едкий комментарий к реальным новостям, оставаясь при этом вымышленными.
- **Слой на техно-сатиру** (как твоя картинка про Claude/Mythos) — это безопаснее политики и часто заходит не хуже.

**Важная практическая оговорка, не юридическая консультация:** сатира на политику в публичном RU-канале — это область реального регуляторного риска (законы о «дискредитации», диффамация и т.п.), которая зависит от конкретных формулировок и контекста, а не только от того, названо ли имя. Разумный компромисс для архитектуры — встроить **шаг ручной модерации перед публикацией на старте** (бот присылает тебе картинку на утверждение перед авто-постом), а не полностью автономный пайплайн с первого дня. Как правило это одна кнопка «опубликовать/пропустить» в самом Telegram-боте — то есть автоматизация всё равно на 95%, просто с чекпоинтом перед выходом в паблик.

## 4. Модель данных (Supabase/Postgres)

```sql
-- Слова от пользователей
create table words (
  id uuid primary key default gen_random_uuid(),
  user_id bigint not null,
  username text,
  word text not null,
  created_at timestamptz default now(),
  likes int default 0
);

-- Новостной фон дня
create table news_items (
  id uuid primary key default gen_random_uuid(),
  source text,
  headline text,
  url text,
  collected_at timestamptz default now()
);

-- Готовые выпуски
create table issues (
  id uuid primary key default gen_random_uuid(),
  date date not null,
  prompt_used text,
  image_url text,
  top_words jsonb,
  top_news jsonb,
  status text default 'draft', -- draft | approved | published
  published_at timestamptz,
  winner_guess_id uuid -- ссылка на лучшую разгадку, победитель попадёт в следующий выпуск
);

-- Разгадки/комментарии пользователей к картинке
create table guesses (
  id uuid primary key default gen_random_uuid(),
  issue_id uuid references issues(id),
  user_id bigint not null,
  username text,
  text text not null,
  votes int default 0,
  created_at timestamptz default now()
);

-- Промежуточные версии картинки в процессе согласования с админом
create table issue_drafts (
  id uuid primary key default gen_random_uuid(),
  issue_id uuid references issues(id),
  prompt_used text,
  image_url text,
  admin_feedback text, -- правка, с которой была сделана следующая версия
  created_at timestamptz default now()
);
```

## 5. ТЗ по модулям (для Antigravity)

### Модуль А — Telegram-бот
- Команды: `/start` (регистрация), отправка любого текстового сообщения = добавление слова.
- Лимит: 1–3 слова в день на пользователя, антиспам через rate-limit по user_id.
- Окно приёма: 00:00–18:00 по МСК (после — бот отвечает «сбор закрыт, жди картинку»).
- Функция лайка чужого слова (опционально, инлайн-кнопки под сообщением-сводкой).

### Модуль Б — Сборщик новостей
- Список RSS-источников (задать конфигом, легко расширять).
- Каждый час — забор новых заголовков, дедупликация по URL.
- К 17:55 — выборка топ-N заголовков дня (по свежести/частоте повторения темы в разных источниках).

### Модуль В — Промпт-инженер
- Системный промпт с жёстко заданной структурой стиля (баннер-заголовок, 3–4 сценки, таблички с текстом, сквозной маскот, мелкие пасхалки по краям) — на входе референс-примеры (можно передать твои 3 картинки как few-shot).
- На входе: топ-слова + топ-новости.
- На выходе: готовый промпт для image API + отдельно — предполагаемая подпись к посту.
- Отдельный подпромпт «редакционная политика» (см. раздел 3) — фильтрует, что уходит в символ/аллегорию.

**Формат брифа (пересмотрено — исходный вариант был слишком абстрактным).** Проблема первого прогона: категории вида «технологический прорыв», «экономический тренд» ничего не говорят о том, что конкретно произошло, и правки промпта вслепую. Каждый пункт брифа должен быть парой «фраза/тег → 1 строка, что это за новость → источник», а не голой категорией:

```
БРИФ ПЛАКАТА ДНЯ (@anta9onist) — 2026-08-07

1. Ключевые новости дня:
   • [ru_hot] «Мэр обещал салют, а взорвался склад петард»
     — источник: Mash, https://...
   • [trends] «Курс доллара» — резкий скачок интереса в Google Trends RU
     — источник: RIA + Google Trends RU
   • [tech] «Anthropic выпустила Claude Sonnet 5»
     — источник: TechCrunch, https://...
   (остальные пункты — по той же схеме: тег категории + суть в одну строку + источник)

2. Топ-слова от читателей:
   • «сатира» — @user1
   • «будущее» — @user2
   (5 слов, без изменений в подходе)

3. Вчерашняя разгадка дня:
   • Победитель: @username
   • Что разгадал: «...» (короткая формулировка)
   • Куда встроить сегодня: пасхалка/подпись/персонаж (на усмотрение)

4. Собранный промпт для image API:
   [полный текст промпта, который реально уйдёт в генерацию]
```

Это даёт тебе возможность править промпт осмысленно — видно, к какой конкретно новости относится каждый фрагмент композиции, а не только абстрактный тег.

### Модуль Г — Image API (абстрактный слой)
- Интерфейс `generateImage(prompt): imageUrl`, под капотом — переключаемый провайдер (gpt-image-1 / Gemini Nano Banana), чтобы AB-тестировать качество на реальном потоке без переписывания остального пайплайна.

### Модуль Д — Модератор (итеративное согласование)
Это диалог с ботом в личке (FSM-состояние на aiogram), а не разовое да/нет:

1. Бот присылает тебе черновик: саму картинку + текст промпта, который был использован для генерации.
2. Под картинкой — две кнопки: **«✅ Опубликовать»** и **«✏️ Доработать»**.
3. Если жмёшь «Доработать» — бот просит написать текстом, что поправить (свободный текст, не структурированная форма). Твоя правка уходит обратно в Модуль В (промпт-инженер) вместе с исходным промптом как контекст: «вот был такой промпт и такая картинка, пользователь просит поправить вот это — перепиши промпт с учётом правки». Получается новый промпт → новая генерация → бот присылает новую версию с теми же двумя кнопками. Цикл повторяется, пока не нажато «Опубликовать».
4. При «Опубликовать»: запись в `issues` получает финальный `prompt_used`, `image_url`, статус меняется на `published`, бот постит картинку в канал (Модуль Е) и одновременно помечает `issue`, чтобы сайт (когда он появится) забрал именно этот `image_url` — то есть повторная генерация «для сайта» не нужна, используется тот же файл, что ушёл в канал.
5. Все промежуточные (неопубликованные) версии тоже стоит хранить в отдельной таблице `issue_drafts` (issue_id, prompt_used, image_url, created_at) — полезно потом посмотреть, как менялась картинка в процессе правок, и это бесплатно по деньгам, только место в БД.

### Модуль Е — Публикатор + архив
- При «Опубликовать» — пост в канал + запись в `issues` со статусом `published`.
- Сайт (фаза 2) читает `issues` напрямую из Supabase.

### Модуль Ж — Расшифровки, голосование и приз (ключевая механика вовлечения)
Логика: после публикации открывается «окно разгадок» (до следующего выпуска, т.е. ~24 часа). Пользователи пишут в комментариях под постом (Telegram-канал с привязанным чатом обсуждений) или боту напрямую свою версию, что зашифровано на картинке.

- **Приём разгадок:** либо реплаи в discussion-группе канала, либо команда боту `/decode <текст>` — под капотом всё равно пишется в таблицу `guesses` с привязкой к `issue_id`.
- **Голосование:** самый дешёвый вариант — реакции (эмодзи) на сообщения в discussion-группе; Telegram Bot API отдаёт события реакций, если бот админ группы — считаем 👍 как голос, никакого отдельного UI не нужно. На сайте (фаза 2) — обычная кнопка «+1» с антифрод-ограничением (1 голос на юзера на комментарий).
- **Подведение итогов:** скрипт по крону в 23:50 выбирает `guess` с максимум `votes` для текущего `issue_id`, пишет его id в `issues.winner_guess_id`.
- **Приз/мотивация:** имя победителя и его формулировка разгадки уходят в промпт-инженер (Модуль В) как обязательный ингредиент **следующей** картинки — например, победитель становится подписью на табличке, именем нового второстепенного персонажа или пасхалкой в углу сцены. Это дешевле любого материального приза и сильнее вовлекает: попасть «в мифологию» интереснее, чем получить абстрактный бейдж.
- Объявление победителя вчерашнего дня — это первая строчка подписи к сегодняшнему посту («Вчера лучше всех разгадал @username — его версия увековечена на сегодняшней картинке в углу у камина»).

## 6. Порядок реализации (спринты)

1. **Спринт 1:** Модуль А (бот собирает слова) + БД. Проверить на своих друзьях 3–4 дня вручную собирая слова.
2. **Спринт 2:** Модуль Б + В — тестировать промпт-инженер отдельно, вручную гонять результат через ChatGPT, пока формула стиля не станет стабильной.
3. **Спринт 3:** Модуль Г + Д — подключить реальный image API + чекпоинт модерации.
4. **Спринт 4:** Модуль Е — автопубликация, первый живой цикл канала.
5. **Спринт 5:** Модуль Ж — комментарии/голосование/победитель в discussion-группе канала. Эту механику стоит включать не позже, чем через 1–2 недели после старта — она основной драйвер возвратов.
6. **Спринт 6 (после недели стабильной работы):** сайт-архив, фаза «прогноз на завтра».
7. **Спринт 7 (фаза 3, только после подтверждённой виральности в RU):** международная версия — см. раздел 8.

## 8. Фаза 3: англоязычная версия (сайт + X/Twitter)

Идея делать это отдельным проектом после обкатки на RU-аудитории — правильная: архитектура (модули А–Ж) переиспользуется почти полностью, меняются только источники и канал дистрибуции.

**Что меняется:**
- Источник новостей — англоязычные RSS-ленты вместо RU.
- Канал дистрибуции — вместо Telegram-канала: сайт + аккаунт в X. Здесь важный практический момент по деньгам: постинг через X API в отличие от Telegram Bot API не бесплатен — платный доступ у X начинается от заметной суммы в месяц за базовый тир с правом постить программно. Это стоит закладывать в бюджет отдельно, когда дойдёте до этой фазы (в отличие от всего остального стека, который бесплатен).
- Механика комментариев/голосования на X устроена иначе (реплаи + лайки вместо discussion-группы) — там разумнее сразу делать голосование через сайт, а X использовать только как канал дистрибуции с ссылкой «разгадать и проголосовать» на сайт.
- Тон сатиры может потребовать отдельной калибровки — нормы уместности сатиры и реакция аудитории в англоязычном сегменте отличаются от RU, плюс в X жёсткая собственная модерация публичного контента — тот же чекпоинт ручного одобрения (Модуль Д) стоит сохранить и здесь на старте.
- Имеет смысл не переводить один и тот же выпуск на два языка, а делать два независимых промпт-контекста (RU новости отдельно, EN новости отдельно) — иначе получится не «зеркало дня» для каждой аудитории, а перевод чужой повестки.

## 9. Источники новостей и пропорции микса

Ключевая мысль по твоему запросу: «горячее» и «скандальное» физически не всегда лежит в классическом RSS — часть таких источников в RU-сегменте живёт нативно в Telegram (без RSS вовсе), поэтому Модуль Б должен уметь читать из двух типов источников: RSS-ленты и Telegram-каналы (через Telethon, как уже заложено в архитектуре).

### A. RU — главные ленты (базовый новостной фон)
- Lenta.ru — `https://lenta.ru/rss` (проверить актуальный путь экспорта на `lenta.ru/info/posts/export/`)
- РИА Новости — `https://ria.ru/export/rss2/archive/index.xml`
- РБК — `https://rssexport.rbc.ru/rbcnews/news/30/full.rss`
- Газета.ru (политика) — `http://www.gazeta.ru/export/rss/politics.xml`
- Газета.ru (общество/скандалы) — `http://www.gazeta.ru/export/rss/social.xml`
- ТАСС — `https://tass.ru/rss/v2.xml`
- Коммерсантъ — список фидов на `kommersant.ru/rss-list`
- Fontanka.ru (питерские расследования и скандалы) — RSS на `fontanka.ru`

### Б. RU — «горячее»/скандальное/таблоид (в основном Telegram, без RSS)
- **Mash** — Telegram-канал, требует Telethon-парсинга, не RSS
- **Baza** — Telegram-канал, аналогично
- **Readovka** — Telegram-канал + сайт (проверить наличие RSS на сайте)
- **112** — сайт + Telegram, часто дублирует резонансные происшествия

### Рекомендуемые пропорции микса (стартовая гипотеза, крутить по факту)

| Категория | Доля в промпте |
|---|---|
| RU горячее/скандальное (Б) | 30% |
| RU общий новостной фон (А) | 20% |
| Google Trends — сигнал вирусности (Д) | 20% |
| Международные скандалы/таблоид (В) | 15% |
| Мировая политика (Г) | 10% |
| Техно/наука (Е) | 5% |

Логика пропорций: категория Д («что реально ищут») — это фильтр правдоподобия для остальных категорий: если тема есть и в новостях, и в Google Trends одновременно — это надёжный кандидат в «главный сюжет дня» картинки. А если тема есть в новостях, но совершенно не искрит в Trends — это, скорее всего, кандидат в мелкую пасхалку сбоку, а не в центр сюжета.

Важно: конкретные RSS-пути у сайтов периодически меняются — при подключении в Antigravity стоит на старте написать простую проверку «жив ли фид» (HTTP-запрос + парсинг первой записи) и сразу отсеять нерабочие адреса, а не полагаться на список статично.
