# ТЗ: Система ранжирования новостей — «Пульс дня»

Документ для Antigravity. Заменяет собой прежний подход с фиксированными категориями и пропорциями (A/Б/В/Г/Д/Е) — от него отказались осознанно: жёсткие квоты по темам создавали перекосы в дни, когда реального материала по какой-то теме объективно мало, а квоту всё равно нужно закрыть. Вместо этого — единый пул новостей из всех источников с математическим скорингом и естественным отбором top-N.

---

## 1. Окно сбора и генерации

Ключевое решение: **окно сбора — плавающие последние 24 часа (18:00 → 18:00), а не календарный день (00:00–18:00)**. Иначе новости, вышедшие в ночь с 18:00 до полуночи, никогда не попадают ни в один выпуск.

- Сбор новостей идёт **непрерывно, круглосуточно** (не только до 18:00) — просто каждый новый цикл сбора кладёт новости в общий пул с меткой времени.
- В 18:00 запускается выборка: `where collected_at >= now() - interval '24 hours'`.
- После выборки топ-10 для сегодняшнего выпуска — эти записи помечаются как использованные (`used_in_issue_id`), чтобы не попасть в выборку повторно завтра, если новость всё ещё будет «свежей» по времени, но уже была показана.
- Всё, что не попало в топ-10, остаётся в базе (не удаляется) — это архив для сайта и потенциальный материал для «широты охвата» (см. ниже), просто не выигравший конкуренцию за конкретный день.

## 2. Модель данных

```sql
create table news_items (
  id uuid primary key default gen_random_uuid(),
  source text not null,                    -- название источника (RSS/Telegram)
  source_url text,
  headline_original text not null,         -- заголовок как есть, любой язык
  ru_headline text,                        -- переведено/переформулировано при оценке
  collected_at timestamptz default now(),

  -- Хард-фильтр (не скор, а бинарный отсекатель)
  has_victims boolean default false,       -- реальные погибшие/пострадавшие/продолжающееся насилие — вне зависимости от темы (война, ДТП, теракт, стихийное бедствие и т.п.)

  -- LLM-оценки, проставляются в момент попадания в базу
  relevance smallint,          -- 1-5: понятно и интересно массовому читателю
  comedic_potential smallint,  -- 1-5: абсурд/юмор/неловкость, "захочется переслать"
  significance smallint,       -- 1-5: масштаб события

  quality_score smallint generated always as (
    coalesce(relevance,0) + coalesce(comedic_potential,0) + coalesce(significance,0)
  ) stored,                    -- 3-15

  -- Кластеризация (широта охвата)
  cluster_id uuid,             -- новости из разных источников об одном событии получают общий id
  breadth_score smallint default 1,  -- увеличивается на 1 за каждый новый независимый источник в кластере

  -- Использование
  used_in_issue_id uuid references issues(id),

  status text default 'pending'  -- pending | scored | rejected_victims | used | archived
);

create index idx_news_collected_at on news_items (collected_at);
create index idx_news_cluster on news_items (cluster_id);
```

## 3. Пайплайн обработки (по шагам)

### Шаг 1 — Сбор (каждый час, круглосуточно)
- Опрос всех RSS-источников + (в будущем) Telegram-каналов.
- Новые записи (дедуп по `source_url`/заголовку) вставляются в `news_items` со `status = 'pending'`.

### Шаг 2 — Оценка (сразу вслед за сбором, микро-батчами по 15-20 новостей за вызов LLM)
Не копить оценку на вечер одним огромным батчем — дорого и хуже калибруется. Оценивать пачками сразу после сбора.

Промпт LLM должен для каждой новости вернуть JSON:
```json
{
  "id": "...",
  "ru_headline": "Мэр обещал салют — взорвался склад петард, пострадавших нет",
  "has_victims": false,
  "relevance": 4,
  "comedic_potential": 5,
  "significance": 2
}
```

**Правила для промпта:**
- `has_victims` — жёсткий вопрос "есть ли в новости реальные погибшие/пострадавшие/продолжающееся насилие", независимо от домена. Дать в системном промпте 2-3 примера-якоря на грани (например: взрыв склада без пострадавших → false, можно шутить; атака с погибшими → true, нельзя) — иначе граница плывёт на неоднозначных заголовках ("инцидент", "ЧП").
- Если `has_victims = true` — дальше не считаем `relevance/comedic_potential/significance`, сразу `status = 'rejected_victims'`, запись остаётся в базе для истории, но никогда не участвует в выборке.
- `comedic_potential` — ось абсурда/юмора/неловкости, не "доброты". Политический ляп или неловкая ситуация оценивается высоко наравне с бытовым курьёзом — ось не должна штрафовать тему только за то, что она политическая, если сама новость смешная, а не трагическая (это и есть разница между "шутить нельзя" и "шутить не о том").
- Оценивать батчами по 15-20 новостей, не по 100 сразу — так LLM стабильнее держит калибровку 1-5 по всему диапазону, а не сжимает оценки к середине.

### Шаг 3 — Кластеризация (широта охвата)
После оценки новой записи — сравнить её с уже вставленными за последние 24 часа (эмбеддинг-схожесть заголовков или, для MVP, более простая эвристика по ключевым словам/именам собственным).

- Совпадение выше порога → присвоить тот же `cluster_id`, что у существующей записи, и **увеличить `breadth_score` на 1 у всех записей этого кластера** (не создавать дубль в топе).
- Не совпадение → новый `cluster_id` = собственный `id` записи, `breadth_score = 1`.

### Шаг 4 — Расчёт актуальности и выборка (в 18:00)
Актуальность не хранится как статичное число — считается на лету по формуле, которую ты задал: старт 6, минус 1 каждые 4 часа.

**Важно: выборка должна брать не более одной новости на кластер**, иначе одна и та же новость из разных источников (с похожими, но не идентичными баллами) может попасть в топ-10 дважды — именно то, с чем уже сталкивались. Дедуп делается через `row_number() over (partition by cluster_id ...)` — из кластера в кандидаты на топ-10 проходит только его лучший представитель по `total_score`.

```sql
with scored as (
  select *,
    quality_score,
    breadth_score,
    greatest(0, 6 - floor(extract(epoch from (now() - collected_at)) / 3600 / 4))::int as freshness_score
  from news_items
  where collected_at >= now() - interval '24 hours'
    and status = 'scored'
),
totals as (
  select *,
    (quality_score + breadth_score + freshness_score) as total_score
  from scored
),
deduped as (
  select *,
    row_number() over (
      partition by cluster_id
      order by total_score desc, collected_at asc
    ) as rn_in_cluster
  from totals
)
select *
from deduped
where rn_in_cluster = 1   -- только лучший представитель каждого кластера
order by total_score desc
limit 10;
```

Топ-10 из этого запроса — кандидаты в сегодняшний бриф (раздел «Ключевые новости дня», формат уже согласован ранее: тег/фраза → 1 строка сути → источник).

После формирования брифа: у выбранных записей `status = 'used'`, `used_in_issue_id = <id текущего issue>`. У остальных записей того же кластера (не прошедших `rn_in_cluster = 1`) имеет смысл проставить `status = 'archived'`, чтобы не участвовали в выборках следующих дней как "непросмотренные" — они уже были представлены своим кластером.

## 4. Крайние случаи

- **Пустой/слабый день** (мало новостей набрали высокий `total_score`): не задавать жёсткий порог отсечения — брать топ-10 по сортировке, даже если абсолютные баллы невысокие. Жёсткий порог (например, "не меньше 8 баллов") в тихий день оставит пустой бриф — это хуже, чем взять то, что есть.
- **Качество кластеризации на шаге 3** — от него напрямую зависит, сработает ли дедуп из раздела 4. Для MVP простая эвристика по ключевым словам/именам собственным может не склеить два заголовка о одном событии, если они сформулированы по-разному ("склад петард взорвался" vs "пожар на пиротехническом складе"). Надёжнее — эмбеддинг-схожесть заголовков (косинусное расстояние) с порогом, подобранным на реальных данных первых недель, а не жёстко зашитым с самого начала. Если кластеризация не склеит дубли — дедуп в разделе 4 их не поймает, и старая проблема повторов вернётся не из-за отсутствия защиты, а из-за пропуска на более раннем шаге.
- **Заголовки на иностранных языках** — перевод/литературная адаптация в `ru_headline` делается сразу на шаге оценки (Шаг 2), а не откладывается на момент попадания в топ — так в архиве (сайт, фаза 2) не остаются непереведённые "хвосты".

## 5. Что осталось прежним (не меняется этим ТЗ)

- Источники и их адреса — без изменений (файл `источники-новостей-и-пропорции.md`), но сам список пропорций по категориям (A/Б/В/Г/Д/Е) в логике отбора больше не используется как квота — категории можно оставить только как справочную метку источника (аналитика постфактум: "сколько в итоге прошло из желтой прессы vs из основных лент"), не как параметр алгоритма.
- Формат брифа (тег → строка сути → источник) и модерация с итеративной правкой (Модуль Д) — без изменений, просто источником топ-10 теперь выступает SQL-запрос из раздела 4 этого документа, а не LLM-выбор из 100 кандидатов разом.
