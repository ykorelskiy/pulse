# ТЗ: Система ранжирования новостей — «Пульс дня»

Документ для Antigravity. **Версия 2.**

Заменяет собой прежний подход с фиксированными категориями и пропорциями
(A/Б/В/Г/Д/Е) — от него отказались осознанно: жёсткие квоты по темам создавали
перекосы в дни, когда реального материала по какой-то теме объективно мало,
а квоту всё равно нужно закрыть. Вместо этого — единый пул новостей из всех
источников с математическим скорингом и естественным отбором top-N.

**Цель продукта:** топ-10 новостей дня — интересных, виральных, позитивных
(или как минимум не гнетущих). Отбор полностью детерминирован SQL-запросом;
LLM участвует только в оценке отдельных новостей, а не в финальном выборе.

---

## 1. Окно сбора и генерации

Ключевое решение: **окно сбора — плавающие последние 24 часа
(18:00 → 18:00), а не календарный день (00:00–18:00)**. Иначе новости,
вышедшие с 18:00 до полуночи, никогда не попадают ни в один выпуск.

- Все времена — в одной явно заданной таймзоне выпуска
  (`Europe/Moscow`, конфигурируемо). «18:00» везде ниже — это 18:00 этой зоны,
  в БД всё хранится в `timestamptz`.
- Сбор новостей идёт **непрерывно, круглосуточно** — каждый цикл сбора кладёт
  новые записи в общий пул с меткой времени.
- В 18:00 запускается выборка:
  `where collected_at >= now() - interval '24 hours'`.
- Выбранные в топ-10 записи помечаются (`status = 'used'`,
  `used_in_issue_id`), чтобы не попасть в выборку повторно завтра, когда
  новость всё ещё «свежая» по времени, но уже была показана.
- Всё, что не попало в топ-10, остаётся в базе (не удаляется) — это архив для
  сайта и материал для аналитики; записи просто не выиграли конкуренцию за
  конкретный день.

## 2. Модель данных

```sql
create table issues (
  id uuid primary key default gen_random_uuid(),
  issue_date date not null unique,
  published_at timestamptz,
  created_at timestamptz default now()
);

create table news_items (
  id uuid primary key default gen_random_uuid(),
  source text not null,                    -- название источника (RSS/Telegram)
  source_url text,
  headline_original text not null,         -- заголовок как есть, любой язык
  headline_hash text not null,             -- md5(normalize(headline_original)) — второй ключ дедупа
  ru_headline text,                        -- переведено/переформулировано при оценке
  collected_at timestamptz default now(),

  -- Хард-фильтр (не скор, а бинарный отсекатель)
  has_victims boolean default false,       -- реальные погибшие/пострадавшие/продолжающееся
                                           -- насилие — вне зависимости от темы (война, ДТП,
                                           -- теракт, стихийное бедствие и т.п.)

  -- LLM-оценки, проставляются сразу после сбора
  relevance smallint,          -- 1-5: понятно и интересно массовому читателю
  comedic_potential smallint,  -- 1-5: абсурд/юмор/неловкость, «захочется переслать»
  significance smallint,       -- 1-5: масштаб события
  tone smallint,               -- -1 / 0 / +1: гнетущая / нейтральная / позитивная
                               -- (мягкий модификатор, НЕ фильтр — см. §3, шаг 2)

  quality_score smallint generated always as (
    coalesce(relevance,0) + coalesce(comedic_potential,0)
    + coalesce(significance,0) + coalesce(tone,0)
  ) stored,                    -- диапазон 2–16

  -- Кластеризация (широта охвата)
  cluster_id uuid,             -- новости из разных источников об одном событии
                               -- получают общий id; breadth НЕ хранится —
                               -- считается на лету в выборке (см. §3, шаг 4)
  embedding vector(1536),      -- pgvector; эмбеддинг ru_headline (фаза 2 — обязателен,
                               -- MVP может стартовать на эвристике без него)

  -- Использование
  used_in_issue_id uuid references issues(id),

  status text not null default 'pending',
  -- pending          — собрана, ждёт оценки
  -- scored           — оценена, участвует в выборках
  -- rejected_victims — отсечена хард-фильтром, хранится для истории
  -- used             — вошла в выпуск
  -- archived         — представлена своим кластером / кластер уже был в выпуске

  constraint uq_source_url unique (source_url),
  constraint uq_headline unique (source, headline_hash)
);

create index idx_news_collected_at on news_items (collected_at);
create index idx_news_cluster on news_items (cluster_id);
create index idx_news_scored on news_items (collected_at) where status = 'scored';
create index idx_news_pending on news_items (id) where status = 'pending';
```

Замечание: `breadth_score` из первой версии убран как хранимое поле.
Инкремент «+1 всем записям кластера» при вставке подвержен гонкам
(параллельные циклы сбора), двойному счёту одного и того же источника
и рассинхрону при пере-кластеризации. Широта охвата теперь вычисляется
в момент выборки как `count(distinct source)` по кластеру — это всегда
консистентно и не требует апдейтов.

## 3. Пайплайн обработки (по шагам)

### Шаг 1 — Сбор (каждый час, круглосуточно)
- Опрос всех RSS-источников + (в будущем) Telegram-каналов.
- Дедуп при вставке — по двум ключам: `source_url` **и**
  `(source, headline_hash)`, где `headline_hash` — хэш нормализованного
  заголовка (lower, trim, схлопнутые пробелы, срезанные UTM-параметры из URL).
  Один `source_url` ненадёжен: источники переопубликовывают материал под
  новым URL или добавляют трекинг-хвосты.
- Новые записи вставляются со `status = 'pending'`.

### Шаг 2 — Оценка (сразу вслед за сбором, микро-батчами по 15–20 новостей)
Не копить оценку на вечер одним огромным батчем — дорого и хуже калибруется.
Оценивать пачками сразу после сбора.

Промпт LLM для каждой новости возвращает JSON:

```json
{
  "id": "...",
  "ru_headline": "Мэр обещал салют — взорвался склад петард, пострадавших нет",
  "has_victims": false,
  "relevance": 4,
  "comedic_potential": 5,
  "significance": 2,
  "tone": 1
}
```

**Правила для промпта:**
- `has_victims` — жёсткий вопрос «есть ли в новости реальные
  погибшие/пострадавшие/продолжающееся насилие», независимо от домена.
  Дать в системном промпте 2–3 примера-якоря на грани (взрыв склада без
  пострадавших → `false`, можно шутить; атака с погибшими → `true`, нельзя) —
  иначе граница плывёт на неоднозначных заголовках («инцидент», «ЧП»).
  **Правило неопределённости: если из заголовка непонятно, есть ли
  пострадавшие, — считать `has_victims = true`** (ложное отсечение дешевле,
  чем шутка над трагедией).
- Если `has_victims = true` — остальные оси не считаем, сразу
  `status = 'rejected_victims'`; запись остаётся в базе для истории, но
  никогда не участвует в выборке.
- `comedic_potential` — ось абсурда/юмора/неловкости, не «доброты».
  Политический ляп или неловкая ситуация оценивается высоко наравне с бытовым
  курьёзом — ось не должна штрафовать тему только за то, что она политическая,
  если сама новость смешная, а не трагическая (разница между «шутить нельзя»
  и «шутить не о том»).
- `tone` — мягкий модификатор под продуктовую цель «позитивные новости»:
  `has_victims` отсекает трагедии, но не гнетущие новости без жертв
  (эпидемии, массовые банкротства, мрачные прогнозы). `-1` слегка топит такие
  новости в ранжировании, `+1` слегка поднимает светлые — **не** отсекая
  важное-но-невесёлое полностью.
- Оценивать батчами по 15–20 новостей, не по 100 — так LLM стабильнее держит
  калибровку 1–5 по всему диапазону, а не сжимает оценки к середине.
- **Валидация ответа:** JSON парсится по схеме; оценки вне диапазона или
  битый JSON → 1 повторный вызов; после повторной ошибки запись остаётся
  `pending` и попадает в следующий батч (не блокирует остальные).
- Перевод/адаптация в `ru_headline` делается здесь же, на шаге оценки, а не
  при попадании в топ — чтобы в архиве (сайт, фаза 2) не оставались
  непереведённые «хвосты».

### Шаг 3 — Кластеризация (широта охвата)
После оценки записи — сравнить её с записями за последние 24 часа
(включая уже `used`/`archived` — важно, см. ниже).

- **MVP:** эвристика по пересечению ключевых слов / имён собственных
  из `ru_headline`.
- **Фаза 2:** эмбеддинг `ru_headline` (единый язык повышает качество
  сравнения), pgvector, косинусная близость. Порог подбирается на реальных
  данных первых недель (стартовая точка ~0.85), не зашивается жёстко.
- Совпадение выше порога → записи присваивается `cluster_id` существующей
  записи. Никаких инкрементов счётчиков — широта считается в выборке.
- Нет совпадения → `cluster_id = id` самой записи (кластер из одного элемента).
- **Кластер уже был в выпуске** (в кластере есть запись со
  `status in ('used','archived')` и заполненным `used_in_issue_id` у кого-либо
  из кластера) → новая запись сразу получает `status = 'archived'`.
  Иначе новость из свежего источника про вчерашнее событие «воскресает» и
  попадает в завтрашний топ как новая. Исключение (существенное развитие
  события) в этой версии не автоматизируем — при необходимости решается
  руками на модерации.

### Шаг 4 — Расчёт актуальности и выборка (в 18:00)
Актуальность не хранится — считается на лету: старт 6, минус 1 каждые 4 часа,
не ниже 0.

Итоговый балл: `total_score = quality_score + breadth_score + freshness_score`,
где:
- `quality_score` — 2–16 (из §2);
- `breadth_score` — число независимых источников в кластере,
  **с потолком 5** (`least(count(distinct source), 5)`): без потолка событие
  с 15 перепечатками задавит оси качества и свежести чистым тиражом;
- `freshness_score` — 0–6.

**Не более одной новости на кластер** — иначе одно событие из разных
источников (с похожими, но не идентичными баллами) попадёт в топ-10 дважды,
что уже случалось. Из кластера проходит лучший представитель по `total_score`.

```sql
with pool as (
  select *
  from news_items
  where collected_at >= now() - interval '24 hours'
    and status = 'scored'
),
scored as (
  select p.*,
    least(count(distinct p.source) over (partition by p.cluster_id), 5)
      as breadth_score,
    greatest(
      0,
      6 - floor(extract(epoch from (now() - p.collected_at)) / 3600 / 4)
    )::int as freshness_score
  from pool p
),
totals as (
  select *,
    (quality_score + breadth_score + freshness_score) as total_score
  from scored
),
deduped as (
  select *,
    row_number() over (
      partition by cluster_id
      order by total_score desc, collected_at asc
    ) as rn_in_cluster
  from totals
)
select *
from deduped
where rn_in_cluster = 1
order by total_score desc, collected_at desc
limit 10;
```

Топ-10 из этого запроса — кандидаты в сегодняшний бриф (раздел «Ключевые
новости дня», формат согласован ранее: тег/фраза → 1 строка сути → источник).

После формирования брифа, **одной транзакцией**:
1. создаётся запись в `issues`;
2. у выбранных записей: `status = 'used'`, `used_in_issue_id = <issue>`;
3. у остальных записей тех же кластеров: `status = 'archived'`,
   `used_in_issue_id = <issue>` — они уже представлены своим кластером и не
   должны участвовать в выборках следующих дней как «непросмотренные».

## 4. Крайние случаи

- **Пустой/слабый день** (мало новостей с высоким `total_score`): жёсткий
  порог отсечения не задаём — берём топ-10 по сортировке, даже если абсолютные
  баллы невысокие. Порог вида «не меньше 8 баллов» в тихий день оставит пустой
  бриф — это хуже, чем взять то, что есть. Если в пуле меньше 10 кластеров —
  бриф выходит коротким, это допустимо.
- **Качество кластеризации (§3, шаг 3)** — от него напрямую зависит, сработает
  ли дедуп в выборке (§3, шаг 4). Эвристика по ключевым словам может не
  склеить два заголовка об одном событии, сформулированные по-разному
  («склад петард взорвался» vs «пожар на пиротехническом складе»). Если
  кластеризация не склеила дубли — дедуп по `cluster_id` их не поймает, и
  проблема повторов вернётся не из-за отсутствия защиты, а из-за пропуска на
  раннем шаге. Поэтому переход на эмбеддинги — приоритет фазы 2, а до него —
  визуальная проверка дублей на модерации.
- **Записи, застрявшие в `pending`** (LLM дважды вернула невалидный ответ,
  сбой батча): подхватываются следующим циклом оценки; записи старше 24 часов
  в `pending` — алерт в мониторинг (§6), в выборку они не попадают by design
  (`status = 'scored'`).
- **Сбой выборки в 18:00 / повторный запуск:** формирование выпуска
  идемпотентно по `issues.issue_date` (unique) — повторный запуск в тот же
  день не создаёт второй выпуск и не помечает записи дважды.

## 5. Что осталось прежним (не меняется этим ТЗ)

- Источники и их адреса — без изменений (файл
  `источники-новостей-и-пропорции.md`), но список пропорций по категориям
  (A/Б/В/Г/Д/Е) в логике отбора больше не используется как квота — категории
  можно оставить как справочную метку источника (аналитика постфактум:
  «сколько прошло из жёлтой прессы vs из основных лент»), не как параметр
  алгоритма.
- Формат брифа (тег → строка сути → источник) и модерация с итеративной
  правкой (Модуль Д) — без изменений; источником топ-10 теперь выступает
  SQL-запрос из §3 (шаг 4), а не LLM-выбор из 100 кандидатов разом.

## 6. Метрики и калибровка (минимум для первых недель)

Не блокирует запуск, но без этого нельзя тюнить пороги:

- **Распределение LLM-оценок по осям** (гистограммы relevance /
  comedic_potential / significance за неделю): если оценки сжимаются к 3–4 —
  править промпт/якоря, а не формулу.
- **Доля `rejected_victims`** по источникам — аномальный рост у источника =
  сигнал проверить якоря промпта или сам источник.
- **Качество кластеризации:** ручная разметка ~50 пар заголовков в неделю
  (дубль/не дубль) → precision/recall текущего порога; на этом подбирается
  порог эмбеддинг-схожести.
- **Правки модерации:** сколько новостей из топ-10 модератор
  выкидывает/заменяет — главная интегральная метрика качества всего скоринга.
- **Алерты:** пустой цикл сбора у источника > N часов; записи в `pending`
  старше 24 ч; невалидные ответы LLM подряд.
