# PULSE — ПЛАН РЕАЛИЗАЦИИ

Принцип: каждый спринт заканчивается **работающим целиком**, пусть и узким,
куском продукта. Никаких «сделаем всё и включим».

---

## Спринт 0 — Каркас (2–3 дня)

- Репозиторий (публичный), структура папок, `pyproject.toml`, pre-commit.
- Supabase-проект, миграция `001_init.sql`, Cloudflare R2 bucket.
- M0: конфиг, репозитории, storage-клиент.
- Заглушки всех остальных модулей с корректными интерфейсами.
- CI: линт + тесты на каждый push.

**Готово, когда:** `python -m pulse.config --check` зелёный, миграция применена,
тестовый файл загружается в R2 и открывается по публичной ссылке.

---

## Спринт 1 — Бот собирает слова (3–4 дня)

- M1 целиком, деплой на Render Free в webhook-режиме, keepalive-пинг.
- Ручная проверка на друзьях: 3–4 дня реального сбора слов.

**Готово, когда:** 5+ реальных людей прислали слова, лимит 1/24ч работает,
данные в БД.

**Что проверяем на людях:** понятны ли правила без объяснений,
не раздражает ли лимит, какие слова присылают на самом деле
(это откалибрует Promptsmith).

---

## Спринт 2 — Новости и темы дня (3–4 дня)

- M2 (RSS-адаптер, `sources.yaml`, job `collect` в GitHub Actions).
- M3 (кластеризация, ранжирование, LLM-формулировка сути).

**Готово, когда:** три дня подряд топ-5 тем субъективно совпадают
с реальной повесткой. Зафиксировать 3 среза в `tests/fixtures/`.

---

## Спринт 3 — Promptsmith и формула стиля (5–7 дней, самый важный)

- Загрузить 4–6 существующих постеров в `style_assets` как референсы.
- Сформулировать Style DNA и layout grid в `config/style.yaml`.
- M4: три стадии (Editorial Policy → Scene Composer → Prompt Builder).
- **Прогонять вручную, без автоматизации**, пока формула не станет стабильной:
  20+ генераций подряд, оценка «узнаётся ли рука художника».

**Готово, когда:** 8 из 10 сгенерированных картинок подряд выглядят
как один и тот же проект, и ни одна не нарушает редакционную политику.

**Не переходить дальше, пока это не достигнуто.** Всё остальное —
обвязка вокруг этого модуля.

---

## Спринт 4 — Генерация и контроль качества (4–5 дней)

- M5: провайдеры Nano Banana Pro + GPT Image 2, фабрика, фолбэк.
- QA-OCR Gate с политикой повторов.
- Гибридный оверлей — минимальная версия для главного баннера.
- Учёт стоимости, дневной лимит расходов.

**Готово, когда:** на выборке из 20 генераций доля картинок с корректной
кириллицей после QA-цикла ≥ 95%; смена провайдера — одной переменной.

**Здесь же — AB-тест:** 10 выпусков на Nano Banana Pro, 10 на GPT Image 2,
сравнить стоимость, латентность, долю прохождения QA с первой попытки
и субъективное качество стиля. Победитель становится основным в конфиге.

---

## Спринт 5 — Модерация и первый живой цикл (4–5 дней)

- M6 (FSM согласования с итерациями).
- M7 (публикация, подпись, hi-res файл).
- M10 (job `daily` в GitHub Actions).

**Готово, когда:** 7 дней подряд канал получает выпуск без ручного
вмешательства в код. Это точка **запуска канала**.

Параллельно: первый пост в личном блоге автора — «я делаю вот такую штуку»
с 3–4 лучшими картинками.

---

## Спринт 6 — Вовлечение (3–4 дня)

- M8: discussion-группа, приём разгадок, реакции как голоса,
  job `winner`, победитель в промпте следующего дня.

**Дедлайн: не позже 2 недель после запуска канала.** Без этой механики
канал — просто лента картинок, с ней — игра, в которую возвращаются.

**Готово, когда:** три дня подряд есть победитель, и его формулировка
физически видна на следующей картинке.

---

## Спринт 7 — Заказные плакаты (5–6 дней)

- M9: бриф-FSM, прайс, оплата, генерация в 4K, гибридный рендер имени,
  согласование с заказчиком, выдача.
- Портфолио из существующих работ («Наташа», «Кораблестроитель», «ВМФ»)
  как публичные примеры.
- CTA в подписи каждого выпуска.

**Готово, когда:** оформлен и выдан первый платный заказ.

**Здесь же — переход на Tier 1** (VPS вместо Render): с момента, когда бот
обслуживает платящих клиентов, засыпающий хост неприемлем.

## Спринт 9+ — Развитие (по факту трафика)

| Что | Триггер запуска |
|---|---|
| «Прогноз на завтра» + сравнение прогноз/факт | 30+ стабильных выпусков |
| Платный тир «Внутренний круг» | 10k подписчиков |
| Календарь профессиональных праздников → проактивные B2B-продажи | первый корпоративный заказ |
| Telegram-каналы как источники (через RSSHub) | если RSS даёт недостаточно «горячей» повестки |
| Регистрация в РКН + пост-выпуск об этом | 10k подписчиков |
| Годовой альбом | 365 выпусков |
| White-label «Пульс компании» | 2+ входящих корпоративных запроса |
| EN-версия | подтверждённая виральность в RU |

## Контрольные точки «стоп/продолжай»

| Момент | Вопрос | Если «нет» |
|---|---|---|
| Конец спринта 3 | Стиль узнаваем и стабилен? | не идти дальше, дорабатывать промпт |
| Конец спринта 5 | 7 выпусков подряд без ручных правок кода? | чинить пайплайн, не добавлять фич |
| +2 недели после запуска | Есть разгадки хотя бы от 5 человек в день? | пересмотреть механику, не масштабировать |
| +1 месяц | Растёт ли аудитория органически? | проблема в контенте, не в дистрибуции |
| +2 месяца | Есть хоть один платный заказ? | пересмотреть продукт №2 или его подачу |

## Порядок для Antigravity

Модули подавать агенту в порядке: M0 → M1 → M2 → M3 → M4 → M5 → M6 → M7 →
M8 → M9 → M10 → M11.

Для каждого модуля давать агенту: раздел ТЗ + релевантный раздел архитектуры
+ уже существующие интерфейсы из предыдущих модулей. Не давать весь документ
целиком — контекст размывается, агент начинает изобретать лишнее.

После каждого модуля: прогон тестов, ручная проверка CLI-точки входа,
коммит. Только потом следующий.
