# PULSE — ТЗ ПО МОДУЛЯМ (для Antigravity)

Формат каждого модуля: назначение → зависимости → интерфейс → требования →
критерии приёмки → тесты. Модули упорядочены по порядку реализации.
Общее правило для агента: Python 3.12, type hints обязательны, pydantic
для моделей данных, structlog для логов, pytest для тестов,
никаких сетевых вызовов в юнит-тестах (мокать провайдеров).

---

## M0 — Ядро: конфиг, БД, хранилище

**Назначение.** Фундамент, от которого зависят все остальные модули.

**Состав.**
- `config.py` — загрузка `.env` + YAML-конфигов в типизированные pydantic-модели
  (`Settings`, `SourcesConfig`, `StyleConfig`, `EditorialConfig`, `PricingConfig`).
  Валидация при старте: отсутствие обязательного ключа = падение с внятным
  сообщением, а не `None` где-то в середине пайплайна.
- `db/client.py` — синглтон-клиент Supabase.
- `db/repo.py` — репозитории: `UsersRepo`, `WordsRepo`, `NewsRepo`, `IssuesRepo`,
  `DraftsRepo`, `GuessesRepo`, `OrdersRepo`, `StyleRepo`, `EventsRepo`.
  Никакого сырого SQL за пределами репозиториев.
- `db/migrations/` — SQL-миграции (нумерованные файлы, применяются вручную
  через Supabase SQL Editor на Tier 0).
- `publisher/storage.py` — обёртка над Cloudflare R2 (boto3, S3-совместимый API):
  `upload(bytes, key) -> public_url`, `download(key) -> bytes`.

**Критерии приёмки.**
1. `python -m pulse.config --check` печатает текущую конфигурацию с
   замаскированными секретами и завершается с кодом 0.
2. Все таблицы из раздела 6 архитектуры созданы миграцией `001_init.sql`.
3. `StorageClient.upload()` возвращает публично доступный URL.
4. Повторная запись выпуска за ту же дату вызывает `DuplicateIssueError`.

## M1 (Модуль А) — Telegram-бот: сбор слов

**Назначение.** Приватный канал ввода данных от пользователей.

**Зависимости.** M0.

**Технологии.** aiogram 3.x, режим **webhook** (не polling — под serverless-хост).
FastAPI как ASGI-обёртка для webhook-эндпоинта.

**Требования.**
1. `/start` — регистрация: upsert в `users`, приветствие с объяснением правил
   («присылай одно слово или короткую фразу в день — она попадёт в картинку»).
2. Любое текстовое сообщение вне команд = отправка слова.
   - Лимит: **1 слово в 24 часа** на пользователя (проверка по
     `words.created_at`). Превышение → вежливый отказ с указанием,
     когда можно снова.
   - Валидация: длина 2–60 символов, не только эмодзи, не URL,
     стоп-лист запрещённой лексики из `config/editorial.yaml`.
   - Подтверждение: «Принято. Слово дня: "<слово>". Картинка в 18:00.»
3. Окно приёма: `00:00 – COLLECT_WINDOW_END` по МСК. После закрытия —
   ответ «Сбор на сегодня закрыт, слово уйдёт в завтрашний выпуск»
   (слово всё равно сохраняется, с флагом на следующий день).
4. `/my` — история слов пользователя и попали ли они в выпуски.
5. `/help`, `/about` — правила и ссылка на канал.
6. Middleware: rate-limit (антифлуд 1 сообщение / 2 сек), бан-лист,
   логирование всех апдейтов в `events`.

**Критерии приёмки.**
- Второе слово за сутки отклоняется; после 24 ч — принимается.
- Бот корректно работает через webhook за HTTPS.
- Все хендлеры покрыты тестами с моком Telegram API.

## M2 (Модуль Б) — Сборщик новостей (RSS)

**Назначение.** Новостной фон дня.

**Зависимости.** M0.

**Интерфейс.**

    class SourceAdapter(Protocol):
        source_id: str
        def fetch(self) -> list[NewsItem]: ...

    class RSSAdapter(SourceAdapter): ...
    # фаза 2 — тот же интерфейс:
    class TelegramBridgeAdapter(RSSAdapter): ...

**Требования.**
1. Загрузка `config/sources.yaml`, инстанцирование адаптеров по полю `type`,
   пропуск `enabled: false`.
2. Опрос всех источников раз в час (job `collect`), таймаут 10 сек на источник,
   ошибка одного не роняет остальные.
3. Дедупликация по `url` (upsert с `on conflict do nothing`).
4. Хранение: `headline`, `summary` (первые 300 символов), `published_at`.
5. Ретеншн: записи старше 14 дней удаляются (экономия 500 MB Supabase Free).
6. Флаг `--dry-run` для локального прогона без записи в БД.

**Критерии приёмки.**
- `python -m pulse.jobs.collect --dry-run` печатает количество новых
  заголовков по каждому источнику.
- Недоступный источник логируется как warning, job завершается успешно.
- Повторный запуск не создаёт дублей.

## M3 — Кластеризация и ранжирование тем

**Назначение.** Из сотен заголовков выбрать 5 тем дня.

**Зависимости.** M2.

**Требования.**
1. Нормализация заголовков (нижний регистр, удаление стоп-слов, лемматизация
   через pymorphy3).
2. Кластеризация: TF-IDF + агломеративная кластеризация по косинусному
   расстоянию (порог в конфиге, старт 0.55). Без тяжёлых эмбеддингов на Tier 0.
3. Скоринг кластера: `0.4×свежесть + 0.35×число_источников + 0.25×вес_источников`.
4. Для топ-5 кластеров LLM формулирует суть одним предложением
   и указывает `tone` доминирующего источника.
5. Выход — `list[Topic]` с полями `summary`, `sources`, `score`, `tone`.

**Критерии приёмки.**
- На реальном срезе за сутки топ-5 тем субъективно совпадают с реальной
  повесткой (ручная проверка на 3 разных днях — зафиксировать в
  `tests/fixtures/`).
- Одна и та же новость из 4 лент попадает в один кластер.

## M4 (Модуль В) — Promptsmith: промпт-инженер

**Назначение.** Превратить темы + слова юзеров в промпт для image-API.
Самый важный модуль проекта: качество здесь определяет качество всего.

**Зависимости.** M0, M3, `style_assets`.

**Архитектура — три последовательные стадии.**

**Стадия 1. Editorial Policy (редакционная политика).**
Вход: топ-5 тем. Выход: строгий JSON.

    {
      "topics": [
        {
          "original": "...",
          "allowed": true,
          "treatment": "symbol",        // symbol | absurd | techno | skip
          "visual_code": "герб/здание/животное-символ вместо лица",
          "risk_flags": ["politician_face"],
          "satire_angle": "высмеивается ситуация, не персона"
        }
      ]
    }

Правила (из `config/editorial.yaml`):
- Запрещены узнаваемые лица реальных живых политиков — только символы,
  гербы, характерные здания, животные-символы, повторяющиеся предметы.
- Высмеивается **ситуация**, не физиономия.
- Темы категории «трагедия/жертвы» → `skip`, без исключений.
- Едкий комментарий отдаётся **вымышленным** сквозным персонажам.
- Приоритет техно-сатиры при прочих равных.

**Стадия 2. Scene Composer.**
Вход: очищенные темы + топ-слова юзеров + вчерашняя победившая разгадка +
`sponsor` (если есть). Выход: структурированный сценарий картинки:

    {
      "banner_title": "≤ 5 слов",
      "scenes": [ {"position": "top-left", "description": "...", "caption": "..."} ],
      "signs": ["≤ 5 слов", "..."],          // таблички
      "mascot_action": "что делает маскот",
      "easter_eggs": ["...", "..."],
      "winner_tribute": "как увековечен победитель вчерашнего дня",
      "sponsor_placement": null | "логотип на табличке у камина",
      "footer_moral": "одна строка"
    }

**Жёсткое ограничение: суммарно ≤ 7 текстовых блоков, ≤ 5 слов в каждом.**
Валидатор проверяет это программно и отправляет LLM на переделку при нарушении.

**Стадия 3. Prompt Builder.**
Собирает финальный промпт: `Style DNA` (из `config/style.yaml`) + layout grid +
сценарий + явный блок текстовых строк:

    RENDER THESE EXACT CYRILLIC STRINGS, no transliteration, no invented letters:
    1) "..."  2) "..."  ...

Возвращает `ImageSpec` (промпт + `text_targets` + референсы из `style_assets`)
и отдельно — **подпись к посту** (caption) для Telegram.

**Режим доработки (для Модуля Д).**

    rebuild(previous_prompt: str, previous_image: bytes,
            admin_feedback: str) -> ImageSpec

LLM получает исходный промпт, картинку и правку админа, возвращает
переписанный промпт с сохранением всего, что не просили менять.

**Критерии приёмки.**
1. На тестовом наборе из 10 «острых» тем ни одна не порождает промпт
   с портретом реального политика.
2. Валидатор текстового бюджета срабатывает на заведомо перегруженном сценарии.
3. `rebuild()` с правкой «убери кота, добавь дождь» меняет только эти элементы
   (проверка diff'ом промптов).
4. CLI `python -m pulse.promptsmith --date today --print` печатает промпт
   без генерации картинки — для ручной отладки формулы стиля.

## M5 (Модуль Г) — Слой генерации изображений

**Назначение.** Абстракция над image-API + контроль качества.

**Зависимости.** M0, M4.

**Состав.**
- `base.py` — `ImageSpec`, `ImageResult`, протокол `ImageProvider`
  (см. раздел 5.4 архитектуры).
- `nanobanana_pro.py` — Gemini 3 Pro Image. Передача 4–6 референсов,
  `aspect_ratio`, разрешение, seed.
- `gptimage2.py` — резервный провайдер.
- `factory.py` — выбор по конфигу, автофолбэк при исключении/таймауте (60 сек),
  запись каждой попытки в `generation_attempts` (провайдер, стоимость, латентность).
- `qa_ocr.py` — QA Gate.
- `overlay.py` — гибридный рендер текста.

**QA Gate — детально.**

    @dataclass
    class QAReport:
        found: list[str]
        missing: list[str]
        garbled: list[tuple[str, str]]   # (ожидалось, распознано)
        score: float                     # 0..1
        passed: bool

    def qa_check(image: bytes, text_targets: list[str]) -> QAReport

Алгоритм: vision-модель читает все надписи → нормализация (регистр, ё/е,
пробелы) → для каждой целевой строки ищется лучшее совпадение по
нормализованному Левенштейну → `passed = min(score) >= 0.92`.

Политика повторов в `generate_with_qa()`:
1. Попытка 1 — обычный промпт.
2. Провал → попытка 2 с усиленной инструкцией по тексту и уменьшенным
   числом текстовых блоков.
3. Провал → попытка 3 на резервном провайдере.
4. Провал → возврат результата с флагом `text_warning=True`; админу уходит
   картинка с пометкой «текст под вопросом» и предложением включить
   гибридный рендер.

**Гибридный рендер (`overlay.py`).**
Промпт запрашивает пустые таблички/баннеры; координаты зон возвращает
vision-модель («найди пустые прямоугольные области для текста, отдай bbox»);
Pillow наносит строки шрифтом из `assets/fonts/` с автоподбором кегля.
На Tier 0 достаточно реализации для одного элемента — главного баннера.

**Критерии приёмки.**
1. Смена `IMAGE_PROVIDER` в `.env` меняет провайдера без изменения кода.
2. При искусственном отказе основного провайдера (мок бросает исключение)
   генерация проходит на резервном.
3. `qa_check` на подготовленной картинке с заведомо искажённой надписью
   возвращает `passed=False` и корректный `garbled`.
4. Стоимость каждой генерации пишется в `generation_attempts`.
5. Дневной лимит расходов из конфига блокирует генерацию при превышении.

## M6 (Модуль Д) — Модерация: итеративное согласование

**Назначение.** Чекпоинт «человек в контуре» перед публикацией.

**Зависимости.** M1, M4, M5.

**FSM (aiogram FSMContext), состояния.**

    AWAITING_DECISION  → кнопки [✅ Опубликовать] [✏️ Доработать] [🚫 Пропустить день]
    AWAITING_FEEDBACK  → админ пишет правку свободным текстом
    REGENERATING       → генерация новой версии

**Требования.**
1. По готовности черновика бот шлёт админу в личку: картинку +
   свёрнутый текст промпта + подпись к посту + `QAReport` кратко
   («текст ок» / «⚠️ проверь надписи: ...») + номер версии + накопленную
   стоимость выпуска.
2. «Доработать» → бот просит правку текстом → `promptsmith.rebuild()` →
   `imagegen.generate_with_qa()` → новая версия с теми же кнопками.
   Каждая версия пишется в `issue_drafts` (version, prompt, image_url,
   admin_feedback, qa_report).
3. Возможность править **подпись к посту** отдельно от картинки
   (кнопка «✏️ Только текст поста»).
4. Лимит версий — 6 (конфиг), дальше предупреждение о расходах.
5. Напоминание, если админ не ответил 60 мин. В 23:00 без ответа —
   день помечается `failed`, публикации нет, утром отчёт.
6. «Пропустить день» → статус `failed`, причина в `admin_feedback`.

**Критерии приёмки.**
- Полный цикл из 3 итераций проходит на моках и оставляет 3 записи
  в `issue_drafts` с корректными `version`.
- Состояние FSM переживает перезапуск бота (хранилище состояний — Redis
  на Tier 1, `MemoryStorage` допустим на Tier 0 с оговоркой в README).

## M7 (Модуль Е) — Публикатор и архив

**Назначение.** Вывод готового выпуска в канал.

**Зависимости.** M0, M5, M6.

**Требования.**
1. При «Опубликовать»: загрузка изображения в R2 (два размера: пост и hi-res),
   `sendPhoto` в канал с подписью, сохранение `tg_message_id`,
   статус `published`, `published_at`.
2. Структура подписи:
   - строка 1 — объявление победителя вчерашних разгадок с @username;
   - строка 2–3 — интригующая подводка к сегодняшней картинке
     (без спойлеров, что зашифровано);
   - строка 4 — призыв: «Что здесь зашифровано? Пиши в комментарии»;
   - строка 5 — CTA продукта №2: «Хочешь такой плакат на день рождения — /order»;
   - хэштеги + дата.
3. Публикация hi-res отдельным документом (файлом) для тех, кто хочет
   рассмотреть детали — это отдельная причина зайти в пост.
4. Ретрай отправки: 3 попытки с экспоненциальной паузой.
5. Идемпотентность: если `tg_message_id` уже есть — повторно не публикуем.

**Критерии приёмки.**
- Пост появляется в тестовом канале с корректной подписью и hi-res файлом.
- Повторный вызов не создаёт второй пост.

## M8 (Модуль Ж) — Вовлечение: разгадки, голоса, победитель

**Назначение.** Главный драйвер возвратов аудитории.

**Зависимости.** M1, M7.

**Требования.**
1. **Приём разгадок** двумя путями, оба пишут в `guesses`:
   - `/decode <текст>` в личке бота;
   - реплаи в discussion-группе под постом выпуска (бот — админ группы,
     ловит `message` с `reply_to_message`, сопоставляет с `issues.tg_message_id`).
2. **Голосование** — реакции 👍 в discussion-группе.
   Бот подписан на `message_reaction` (требует прав админа), инкрементирует
   `guesses.votes`. Один пользователь = один голос (Telegram гарантирует).
3. **Окно** — до следующего выпуска (~24 ч). Позднее — «окно закрыто».
4. **Подведение итогов** — job в 23:50: выбор `guess` с максимумом голосов
   за текущий `issue_id`, запись в `issues.winner_guess_id`,
   уведомление победителя в личку.
   Тай-брейк: раньше отправленная разгадка выигрывает.
5. **Приз** — победитель и его формулировка передаются в Promptsmith
   как **обязательный** ингредиент следующей картинки (`winner_tribute`):
   подпись на табличке, имя второстепенного персонажа или пасхалка в углу.
6. Защита от накрутки: голоса от аккаунтов моложе 7 дней в канале не
   учитываются (проверка через `getChatMember` + дата первого события).

**Критерии приёмки.**
- Разгадка из группы и из бота одинаково попадают в `guesses`.
- Реакция 👍 увеличивает счётчик, снятие реакции — уменьшает.
- Job выбирает победителя и его текст реально появляется в промпте
  следующего дня (проверяется наличием подстроки).

## M9 (Модуль З) — Заказные плакаты

**Назначение.** Продукт №2, монетизация с первого дня.

**Зависимости.** M4, M5, M6 (переиспользование FSM согласования).

**Требования.**
1. `/order` запускает бриф-диалог (FSM):
   - тип: день рождения / профессиональный праздник / корпоратив;
   - имя и повод (возраст, должность, компания);
   - 3–7 фактов о человеке: увлечения, привычки, внутренние шутки;
   - фото (для портретного сходства) — опционально, но рекомендуется;
   - формат: электронный / печатный;
   - срок.
2. Расчёт цены по `config/pricing.yaml` (тип × формат × срочность),
   показ итога, подтверждение.
3. Оплата: Telegram Stars (`sendInvoice`) либо ссылка на оплату
   самозанятому. Статус → `paid`.
4. Генерация: тот же Promptsmith в режиме `order`
   (Style DNA тот же, сценарий строится из брифа, не из новостей),
   разрешение 4K, **гибридный рендер обязателен для имени**.
5. Согласование с заказчиком: тот же интерфейс кнопок, что у админа,
   лимит правок `revisions_limit` (по умолчанию 3), сверх — доплата.
6. Выдача: файл в максимальном качестве + версия для печати (300 dpi, CMYK-safe).
7. Все заказы и версии — в `orders` и `generation_attempts`.

**Критерии приёмки.**
- Полный путь `/order → бриф → оплата (тестовый режим) → 2 правки → выдача`
  проходит на моках.
- Имя заказчика на итоговом плакате рендерится программно и всегда корректно.
- Превышение лимита правок блокируется с предложением доплаты.

## M10 — Оркестрация (jobs + GitHub Actions)

**Задания.**

| Job | Расписание (МСК) | Что делает |
|---|---|---|
| `collect` | каждый час | опрос RSS, дедупликация |
| `daily` | 17:15 | кластеризация → промпт → генерация → QA → отправка админу |
| `winner` | 23:50 | подведение итогов разгадок |
| `retention` | 04:00 еженедельно | чистка новостей старше 14 дней |
| `keepalive` | раз в 3 недели | пустой коммит против отключения cron |
| `anti_drift` | воскресенье | сверка стиля недели с референсами, отчёт админу |

**Требования.**
1. Все job'ы — идемпотентны и запускаются вручную (`workflow_dispatch`)
   с параметром даты.
2. Cron в UTC с поправкой на МСК; учитывать, что GitHub задерживает запуск
   на 5–30 мин → `daily` стартует в 17:15, внутри ждёт до `PUBLISH_TIME`
   только на этапе публикации, генерация идёт сразу.
3. Любое необработанное исключение → сообщение админу в Telegram с трейсом.
4. Каждый job пишет старт/финиш/длительность в `events`.

**Критерии приёмки.**
- `workflow_dispatch` с датой в прошлом пересобирает выпуск за тот день.
- Падение job'а порождает алерт в личку админу.

## M11 — Сайт-архив (фаза 2)

**Назначение.** Витрина, SEO, приём заказов вне Telegram.

**Стек.** Next.js (App Router) на Vercel Hobby, чтение напрямую из Supabase
через публичный anon-ключ и RLS-политики (только `status='published'`).

**Страницы.**
- `/` — сегодняшний выпуск крупно;
- `/archive` — календарь-сетка миниатюр;
- `/issue/[date]` — выпуск, подпись, топ-разгадки, ссылка на пост;
- `/order` — лендинг продукта №2 с портфолио (готовые примеры плакатов);
- `/about` — о проекте, открытое авторство, ссылка на личный блог автора.

**Критерии приёмки.**
- Черновики и неопубликованные выпуски недоступны анонимному ключу
  (проверить RLS явным тестом).
- Lighthouse ≥ 90 по производительности на странице выпуска.

## Общие требования к коду (для агента)

1. Все внешние вызовы (Telegram, LLM, image, БД, R2) — за интерфейсами,
   в тестах мокаются. Ни один тест не ходит в сеть.
2. Все деньги — `numeric`/`Decimal`, никаких float для стоимости.
3. Все времена — timezone-aware UTC в БД, конвертация в МСК на границе.
4. Логи — structlog в JSON, с `issue_id`/`order_id` в контексте.
5. Каждый модуль имеет CLI-точку входа для ручного прогона
   (`python -m pulse.<module> --help`).
6. README с разделом «как запустить локально за 10 минут» и
   «как выкатить на Tier 0» — обязательная часть поставки.
7. Ни одного секрета в репозитории; pre-commit с детектором секретов.
